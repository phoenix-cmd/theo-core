## 2. V1–V6 Mathematical & Procedural Validity — UNKNOWN

- **V1 (sensitivity/invariance):** Mathematically sound — a same-meaning paraphrase control over real frozen `psdg_fn` is the correct invariance test. *Procedural gap:* it mandates aggregation "by frozen `cos_H1_aggregate`," which is inconsistent with a *redesigned* observable (see §4). Also no sample count for the fresh set (see §4). → UNKNOWN.
- **V2 / V3 (known-compatible / known-incompatible):** The *form* is sound — requiring high reading on genuinely-aligned constructed cases and low reading on genuinely-misaligned cases, with a separation margin, is exactly the right discriminative-validity structure. *Procedural gap:* the acceptance margins are reasonable, but the **construction method that establishes "known by construction" is undefined** (see §3). Without it, the mathematics cannot be certified as non-circular. → UNKNOWN.
- **V4 (specificity):** Sound — see §5. PASS-grade on the math.
- **V5 (integrity):** Sound — frozen machinery SHA-verified, pre/post SHA manifest, NEPR. PASS-grade.
- **V6 (pre-registration):** Sound in intent. But the *values* it pre-registers (notably V2's 0.80) are not yet justified independently (see §7). → UNKNOWN on completeness.

## 3. Non-Degeneracy of Known-Compatible / Known-Incompatible Controls — UNKNOWN

This is the linchpin of the whole redesign and is currently the weakest point.

- **Degeneracy that V2+V3 DO prevent:** A constant output fails (constant-high fails V3; constant-low fails V2; any single constant fails the required separation). So the pair rules out *trivially constant* instruments. Good.
- **Degeneracy that V2+V3 do NOT prevent — the real risk:** If the "known-compatible" / "known-incompatible" cases are built by *directly injecting* the gradient relationship the instrument measures (e.g., setting PRO and ABS gradients to be identical by fiat, or constructing the case from the instrument's own internal definition), then the test is **tautological**, not a validation. The instrument would "detect" compatibility only because it was built in.
- **What is missing:** a requirement that controlled cases be generated by an **independent causal mechanism** — e.g., a toy model/readout whose aligned subspace exists by its *architecture/weights*, such that the instrument (which only sees the model + prompts) must *discover* the alignment rather than read an injected label. The spec mentions "synthetic/controlled readout or model regime" but does **not** mandate independence of construction from the instrument definition.
- **Conclusion:** V2/V3 non-degeneracy is only as strong as an undefined construction method → **UNKNOWN**. This must be made explicit and mandatory before the spec can pass.

## 4. Exact Sample Counts, Aggregation Rules, Exclusion Rules, Failure Actions — UNKNOWN (counts/exclusion = FAIL; failure action = PASS)

- **Sample counts — FAIL (undefinced):** The original 6E.20.7 SENS used 16 prompts (8 PRO + 8 ABS) and the evaluation aggregated over conditions × {4,6,14,15}. The 6E.20.8 spec proposes acceptance *margins* (0.95 / 0.80 / 0.20 / 0.50) but **specifies no N** for V1–V4 (no number of paraphrase pairs, no number of constructed compatible/incompatible cases, no number of random-direction probes). Without N, "mean ≥ 0.80" and "separation ≥ 0.50" are not statistically meaningful and cannot be audited. **Mandatory correction: pin exact sample counts.**
- **Aggregation rules — UNKNOWN (internal inconsistency):** V1 says the control is "aggregated by frozen `cos_H1_aggregate`." But §3 and §6 state the *observable definition itself may change* in the redesign. If the aggregation changes, V1 testing the *old* frozen `cos_H1_aggregate` would not validate the *new* instrument. The sensitivity control must be applied to whatever the **new** instrument's aggregation is, while only the underlying gradient machinery (`psdg_fn`) stays frozen. The spec must resolve whether the redesign is constrained to keep `cos_H1_aggregate` (then V1 is consistent) or may change it (then V1 must reference the new aggregation).
- **Exclusion rules — FAIL (none defined):** No rule for failed gradient computations, NaNs, outlier steps, or non-convergent controlled cases. **Mandatory correction: define exclusion/handling rules.**
- **Failure actions — PASS:** The global gating rule is explicit and correct: "ALL of V1–V6 must be satisfied. If V1–V4 fail, the instrument is not validated; no new S4/S8 training is authorized, and the redesign iterates at the specification level only." This is a clear, defensible failure action. (No per-criterion partial-failure handling is specified, but the global gate suffices.)

## 5. Specificity Control Against the Correct Null — PASS

- The null for "the readout implements a fixed aligned subspace" is that gradients are effectively structureless/random. **V4 uses a random 1D direction as the null**, which is the correct minimal null. PASS.
- **Minor strengthening (non-blocking):** V4 could be made more robust by using a **random readout vector** (random `w`) rather than only a random 1D *direction within* the existing readout, to guard against an instrument that is specific to the readout's coordinate frame but not to alignment per se. Suggested, not required.
- **Note:** V4 should be defined relative to the *constructed compatible* case (V2), **not** the real S4/S8, to avoid leaking real-data structure into the validation. The spec's wording ("the intended readout direction reads high") is ambiguous on this; clarify to reference the V2 constructed case.

## 6. Sufficiency of V1–V6 to Justify Deployment to S4/S8 — UNKNOWN

- V1–V6, as written, validate the instrument in **synthetic/controlled regimes**. Passing them establishes that the instrument *can* separate known-compatible from known-incompatible gradient relationships under construction. That is necessary but **not sufficient** for deployment to the **real** S4/S8 checkpoints, because of (a) distribution shift between constructed and real models, and (b) the fact that synthetic validation says nothing about whether the *real* S4/S8 exhibit the relationship.
- **Critical gap:** the spec conflates two distinct downstream uses and does not separate them:
  1. **Read-only application of the validated instrument to the existing real S4/S8 checkpoints** (to finally obtain a *valid* measurement of the premise) — this is permissible only under a *fresh, pre-registered authorization* and still does **not** by itself resolve the premise.
  2. **New S4/S8 training** — this requires the premise to be *resolvable*, which synthetic validation alone does not establish.
- **Conclusion:** V1–V6 passing justifies advancing to a *validated-instrument* status in the controlled regime and to a pre-registered read-only application on real S4/S8, but is **NOT sufficient to authorize new S4/S8 training**. The spec must state this explicitly and add the read-only-application gate as a distinct, pre-registered step. → UNKNOWN.

## 7. Absence of Any Tuning Loop Against H1/P2 = 0.80 — UNKNOWN

- **No iterative tuning loop — PASS:** The spec defines no procedure that iterates the instrument to make H1 pass; all thresholds are to be pre-registered (V6). The explicit statement "The H1 ≥ 0.80 threshold is NOT a tuning target … it must not be used to design, fit, or accept the instrument" is correct and should be preserved.
- **Literal reuse of 0.80 in V2 — FAIL-grade smell (must fix):** V2 sets acceptance "instrument mean on known-compatible cases ≥ **0.80**." This is precisely the value the user instructed must **not** be carried into the measurement-validation experiment. Even though the *intent* differs (0.80 as the expected reading on a genuinely-compatible constructed case, not as the H1 decision threshold), the **literal reuse of the number 0.80 invites exactly the conflation the instruction forbids** and risks the appearance of tuning the instrument to "look like H1 would have passed."
- **Required correction:** V2's acceptance margin must be **derived from the constructed ground truth** (e.g., from the known alignment angle θ of the compatible case, expected cos ≈ cos θ), **not** borrowed from the H1 0.80 protocol value. After this change, the validation thresholds (V1 0.95, V2 derived, V3 0.20, separation 0.50) contain no 0.80, fully honoring the instruction.
- Net: the *intent* (no tuning loop) is honored, but the *letter* is violated by V2's 0.80 → UNKNOWN with a mandatory correction.

## 9. Required Corrections (mandatory before advancement)

1. **Pin exact sample counts** for V1 (fresh paraphrase pairs), V2/V3 (number of constructed compatible/incompatible cases), and V4 (random-direction probes). No N → no auditable acceptance.
2. **Define the controlled-case construction method** for V2/V3 with an explicit **independence requirement**: cases generated by an independent causal mechanism (e.g., toy model/readout with alignment by architecture/weights), not by injecting the instrument's own gradient relationship. This is what makes non-degeneracy real.
3. **Decouple V2 from 0.80**: derive V2's acceptance margin from the constructed ground truth, not the H1 protocol value. Remove the literal 0.80 from validation thresholds.
4. **Resolve V1 aggregation scope**: state explicitly whether the redesign is constrained to `cos_H1_aggregate` (then V1 is consistent) or may change aggregation (then V1 must test the *new* instrument's aggregation over frozen `psdg_fn` only).
5. **Define exclusion/handling rules** for failed gradients, NaNs, outlier steps, and non-convergent controlled cases.
6. **Separate the two deployment uses**: state that V1–V6 passing justifies (a) validated-instrument status in the controlled regime and (b) a *pre-registered read-only application* to real S4/S8 under a fresh authorization — but is **NOT sufficient** to authorize new S4/S8 training. Add the read-only-application gate explicitly.
7. **Clarify V4's reference**: define the specificity null relative to the V2 constructed compatible case, not real S4/S8; optionally strengthen to a random-readout null.

---

## 10. Final Authorization Recommendation

**REVISE — CONDITIONAL HOLD. Do NOT authorize implementation, execution, or any S4/S8 training at this time.**

Rationale:
- The specification is **sound in direction and intent**: it correctly opens a measurement-redesign branch (decision B), excludes 0.80 as a tuning target in principle, keeps 6E.20.7 frozen as evidence, uses the correct null for specificity, and defines a clear global failure gate.
- However, it is **procedurally incomplete** on the points that determine whether the validation would actually be valid and non-degenerate: undefined sample counts and exclusion rules (FAIL), an undefined controlled-case construction method that leaves non-degeneracy unverifiable (UNKNOWN), a literal 0.80 reuse in V2 that violates the user's explicit instruction (must fix), an aggregation-scope inconsistency with a redesigned observable, and an unseparated deployment-to-real-S4/S8 step.

This is a **hold for revision, not a rejection**. The scientific path is correct; the specification must be tightened on the seven corrections above, then advanced through the governance chain (independent specification → independent audit → synthetic/controlled validation → human review → implementation → source audit → L5 authorization → only then new intervention).

**No implementation, no execution authorization, and no S4/S8 training follow this audit.**
