# Phase 6E.20.3 — Reproducibility Specification and Environment Provenance Remediation (Revised)

**Status:** PROPOSAL ONLY (revised per human review APPROVE WITH CONDITIONS). No
modification to 6E.20.1, its historical anchor, frozen checkpoints, the halted 6E.20.2
execution record, tolerance, runner, environment settings, or authorization. No rerun.
No model loading or evaluation. No reuse of the current authorization for changed
artifacts.

**Supersedes:** Nothing. This proposal does not amend frozen protocol v3.1
(`E16CA4F1…`). It proposes amendments for human review under a future revision.

**Governing investigation:** Phase 6E.20.2 Stage 5 halt — root cause unresolved
(runtime drift plausible, not proven; Classification B per
`FORENSIC_6E20.2_STAGE5_ROOTCAUSE_EVIDENCE_CHALLENGE.md`).

**Depends on:** Establishment of the historical provenance defect (no environment
metadata in any 6E.20.1 provenance artifact: `runs.json`, `sha256_manifest.json`,
`pre_registration_snapshot.json`, `p5_loo_report.json`).

**Revision note:** This revision incorporates all five conditions from the independent
audit (`6E.20.3_INDEPENDENT_SOURCE_SPECIFICATION_AUDIT.md` §7.1–7.5), approved by
human review. Changes from the original proposal are marked with **[REVISED]** or
**[NEW]**.

## 1. Defect Statement

A numerical reproducibility anchor cannot require cross-run reproduction to a strict
tolerance unless the runtime environment and numerical execution conditions necessary
to interpret that tolerance are themselves recorded and/or specified.

The 6E.20.2 execution exposed two independent specification deficiencies:

**Defect 1 — No environment provenance.** Protocol v3.1 §10.10 specifies provenance
artifacts (sha256_manifest, runs.json, pre_registration_snapshot, p5_loo_report,
reference tensors) but does not require recording any runtime environment metadata
(Python/PyTorch/CUDA/driver versions, GPU model, dtype settings, attention backend,
deterministic flags, seeds). The historical 6E.20.1 execution recorded none. The
historical B0 anchor value (`cos_H1 = 0.428355` at step 4) is therefore
environment-unverifiable: we cannot determine whether the current execution's
environment is equivalent to the historical one.

**Defect 2 — No same/cross-environment distinction.** The 6E.20.2 runner introduced
`B0_REPRODUCIBILITY_TOLERANCE = 1e-4` as an implementation-level constant, applied
uniformly regardless of whether the execution environment matches the historical one.
Protocol v3.1 does not define this tolerance or distinguish same-environment
reproducibility (where a strict tolerance is meaningful) from cross-environment
reproducibility (where it is not).

**This proposal addresses both deficiencies.** It does not claim to identify the cause
of the specific `0.009654` divergence observed in Stage 5. That divergence remains
unresolved (Classification B).

## 2. Proposed Specification Changes

### 2.1 New §5.8 — Numerical Environment Provenance Record

Every future anchor-producing execution MUST emit an immutable **Numerical Environment
Provenance Record** (NEPR) as part of its provenance artifacts. The NEPR is a
JSON-serializable object bound to the execution's protocol hash, runner hash, test-suite
hash, model identity, checkpoint hashes, corpus/input hashes, and output/anchor
identifier.

**[REVISED] Tamper Protection and Cryptographic Binding (audit condition 1):**

The NEPR contains a mandatory `nepr_hash` field: the SHA-256 hash of the JSON-serialized
NEPR *excluding* the `nepr_hash` field itself (i.e., hash of all other fields in
canonical JSON key-sorted order). The `nepr_hash` MUST be included in
`sha256_manifest.json` under a new `"numerical_environment_provenance"` entry. The NEPR
file MUST be written atomically (no partial writes) and MUST NOT be modified after
emission. Any modification invalidates the `nepr_hash` and voids the execution.

The NEPR contains the following mandatory fields:

#### A. Software Identity

| Field | Type | Description |
|---|---|---|
| `python_version` | string | Full Python version (e.g., `"3.14.3"`) |
| `pytorch_version` | string | PyTorch version + build (e.g., `"2.13.0+cu126"`) |
| `cuda_version` | string | CUDA version as reported by `torch.version.cuda` |
| `cudnn_version` | string | cuDNN version as reported by `torch.backends.cudnn.version()` |
| `transformers_version` | string | HuggingFace Transformers version |
| `peft_version` | string | PEFT version |
| `tokenizers_version` | string | Tokenizers version |
| `flash_attn_installed` | boolean | Whether `flash_attn` is importable |
| `flash_attn_version` | string or null | Version if installed, null otherwise |
| `xformers_installed` | boolean | Whether `xformers` is importable |
| `xformers_version` | string or null | Version if installed, null otherwise |
| `other_attention_libs` | object | Key-value pairs for any other attention-related libraries |

#### B. Hardware Identity

**[REVISED] Multi-GPU/Device-Topology Provenance (audit condition 3):**

| Field | Type | Description |
|---|---|---|
| `device_type` | string | `"cuda"`, `"cpu"`, `"mps"`, etc. |
| `gpu_model` | string | GPU name as reported by `torch.cuda.get_device_name(0)` |
| `gpu_count` | integer | Number of devices used |
| `compute_capability` | array[int] | e.g., `[7, 5]` for Turing |
| `nvidia_driver_version` | string | Driver version as reported by `nvidia-smi` or `torch.version` |
| `gpu_memory_gb` | float | Per-device memory in GB |
| `model_parallel` | boolean | Whether model parallelism is used |
| `device_map` | string or null | Device map strategy (e.g., `"cuda:0"`, `"auto"`, `null` for single-device) |
| `world_size` | integer | Total number of processes (1 for single-device) |
| `per_device_batch_size` | integer | Batch size per device |

**Rationale:** Model parallelism or multi-device execution can change reduction order
and accumulation behavior even with identical software. `model_parallel`, `device_map`,
and `world_size` capture the device topology. `per_device_batch_size` distinguishes
data-parallel vs model-parallel splits.

#### C. Numerical Execution Settings

| Field | Type | Description |
|---|---|---|

| `cudnn_deterministic` | boolean | `torch.backends.cudnn.deterministic` |
| `cudnn_benchmark` | boolean | `torch.backends.cudnn.benchmark` |
| `amp_enabled` | boolean | Whether `torch.cuda.amp` or `autocast` is active |
| `attention_backend` | string | Selected attention implementation (e.g., `"sdpa"`, `"eager"`, `"flash_attention_2"`) |
| `gradient_checkpointing` | boolean | Whether gradient checkpointing is active during evaluation |

#### D. Reproducibility State

| Field | Type | Description |
|---|---|---|
| `python_seed` | integer or null | `PYTHONHASHSEED` or explicit seed if set |
| `numpy_seed` | integer or null | NumPy seed if explicitly set |

| `cuda_deterministic` | boolean | Whether CUDA operations are fully deterministic |

#### E. Artifact Binding

| Field | Type | Description |
|---|---|---|

| Field | Type | Description |
|---|---|---|
| `nepr_schema_version` | string | Schema version (e.g., `"1.0"`) |
| `nepr_emission_timestamp` | string | ISO 8601 UTC timestamp of NEPR creation |
| `nepr_hash` | string | SHA-256 of all other NEPR fields (canonical JSON, key-sorted) |

### 2.2 NEPR Schema Versioning and Compatibility **[NEW]** (audit condition 4)

The `nepr_schema_version` field uses semantic versioning (`MAJOR.MINOR`):

- **MAJOR version bump** (e.g., `"1.0"` → `"2.0"`): field additions, removals, or
  type changes that break backward compatibility. A NEPR with MAJOR version `N` is
  **incompatible** with a NEPR of MAJOR version `M ≠ N`. Same-environment comparison
  MUST NOT be performed across MAJOR version differences; the classification defaults
  to `ENVIRONMENT_UNVERIFIABLE`.

- **MINOR version bump** (e.g., `"1.0"` → `"1.1"`): field additions that are
  backward-compatible (new fields have defaults; existing fields unchanged). A NEPR
  with MINOR version `M.x` is **compatible** with a NEPR of MINOR version `M.y`
  (x ≠ y). Missing fields in the older NEPR are treated as `null`/`false`/`0`
  for comparison purposes.

- **PATCH version bump** (e.g., `"1.0.0"` → `"1.0.1"`): editorial corrections that
  do not affect field semantics. Fully compatible.

The initial NEPR schema version is `"1.0"`. Schema changes MUST be documented in a
`nepr_schema_changelog` entry within the NEPR itself (for MINOR/PATCH bumps) or in a
separate schema document (for MAJOR bumps).

### 2.3 Deterministic NEPR Comparison Protocol **[NEW]** (audit condition 2)

When comparing two NEPRs (current execution vs reference execution), the following
deterministic algorithm MUST be applied:

**Step 1 — Schema compatibility check.**
Compare `nepr_schema_version` fields. If MAJOR versions differ → classify as
`ENVIRONMENT_UNVERIFIABLE` and STOP. If MINOR versions differ → proceed with missing
fields treated as defaults.

**Step 2 — Artifact binding check.**
Compare fields in category E (Artifact Binding): `protocol_hash`, `runner_hash`,
`test_suite_hash`, `model_id`, `model_revision`, `checkpoint_hashes`, `corpus_hash`.
All must match exactly (byte-for-byte string equality). If any differ → classify as
`ENVIRONMENT_UNVERIFIABLE` (the executions used different artifacts, not just different
environments) and STOP.

**Step 3 — Environment comparison.**
Compare ALL fields in categories A (Software Identity), B (Hardware Identity), and
C (Numerical Execution Settings) using the following rules:

| Field type | Comparison rule |
|---|---|
| string | Exact string equality (`==`) |
| boolean | Boolean equality (`==`) |
| integer | Integer equality (`==`) |
| float | Float equality (`==`) — not approximate; NEPR values are read from system APIs, not computed |
| array[int] | Element-wise integer equality |
| object (key-value) | Same keys with same values (recursive) |
| null | Null equals null; null does not equal any non-null value |

If ALL A/B/C fields match → classify as `SAME_ENVIRONMENT`.
If ANY A/B/C field differs → classify as `CROSS_ENVIRONMENT`.

**Step 4 — Category D check (informational only).**
Compare category D (Reproducibility State) fields. D differences do NOT affect the
SAME/CROSS classification (seeds and device placement do not affect deterministic
eval-mode inference with fixed inputs). D differences are recorded in the comparison
report for informational purposes.

**Step 5 — Emit comparison report.**
The comparison produces a structured report:
```json
{
  "classification": "SAME_ENVIRONMENT | CROSS_ENVIRONMENT | ENVIRONMENT_UNVERIFIABLE",
  "a_b_c_differences": [ ... ],
  "d_informational_differences": [ ... ],
  "schema_version_current": "...",
  "schema_version_reference": "...",
  "artifact_binding_match": true | false
}
```

### 2.4 Same-Environment vs Cross-Environment Reproducibility

The following distinction MUST be added to §5.7 (or a new §5.8 if §5.7 is frozen):

**Same-environment reproducibility.** A strict numerical tolerance (e.g., `1e-4`) may
be applied when the NEPR comparison (§2.3) classifies the execution as
`SAME_ENVIRONMENT` AND the reference NEPR was recorded at the time of the reference
execution (not retroactively reconstructed).

**Cross-environment reproducibility.** If the NEPR comparison classifies the execution
as `CROSS_ENVIRONMENT`, the execution MUST NOT automatically inherit the same-environment
tolerance. Instead:

- The tolerance for cross-environment comparison MUST be either
  (a) empirically justified by a controlled cross-environment validation study, or
  (b) classified as a separate reproducibility experiment with its own acceptance
  criteria, rather than an exact anchor gate.

The cross-environment tolerance, if defined, MUST be recorded in the NEPR alongside the
same-environment tolerance, with explicit labeling of which tolerance applies under which
conditions.

**Environment-unverifiable reproducibility.** If the NEPR comparison classifies the
execution as `ENVIRONMENT_UNVERIFIABLE` (historical NEPR absent, schema incompatible,
or artifacts differ), the tolerance MUST NOT be applied as a pass/fail gate. The
divergence is recorded but classified as unresolved. **[REVISED]** This classification
does NOT halt execution or prevent §8 evaluation (see §2.7).

### 2.5 Amendment to §10.10 — Provenance Requirements

Protocol v3.1 §10.10 currently specifies: sha256_manifest.json, reference tensors,
runs.json, pre_registration_snapshot.json, p5_loo_report.json, execution_authorization.json.

The following MUST be added:

- **Numerical Environment Provenance Record (NEPR):** a JSON file
  (`numerical_environment_provenance.json`) containing the fields defined in §2.1
  above, emitted at execution time (not post-hoc). The NEPR MUST be written before
  any evaluation gates are evaluated.
- **Anchor Provenance Record:** for any execution that produces a numerical reproducibility
  anchor (e.g., B0 cos_H1 values), an additional record binding the anchor values to the
  NEPR, runner hash, and checkpoint identifiers.
- **NEPR hash in sha256_manifest.json:** the `nepr_hash` MUST be included in
  `sha256_manifest.json` under the key `"numerical_environment_provenance"`.

### 2.6 Revised §10.7 — B0 Collapse Guard and Reproducibility Anchor

The current §10.7 defines the B0 collapse guard (K=3 consecutive zero-proposal steps)
but does not define a reproducibility anchor gate. The following MUST be added:

**B0 Reproducibility Anchor Gate (new).** When a B0 historical reproducibility anchor
is used (i.e., comparing recomputed cos(H1) values against previously recorded values
from a prior execution):

1. The anchor values, their checkpoint indices, and the tolerance MUST be defined in
   the execution plan (not solely in runner code).
2. The NEPR of the current execution MUST be emitted BEFORE the anchor gate is
   evaluated.
3. The NEPR of the current execution MUST be compared against the NEPR of the
   anchor-producing execution using the deterministic protocol (§2.3).
4. The gate MUST report:
   - The NEPR comparison classification (`SAME_ENVIRONMENT`, `CROSS_ENVIRONMENT`,
     or `ENVIRONMENT_UNVERIFIABLE`)
   - The list of any A/B/C field differences
   - The numerical divergence (recomputed vs historical, absolute and relative)
   - Whether the tolerance is applicable under the classification
5. **[REVISED] Effect on execution flow (audit condition 5):**
   - If `SAME_ENVIRONMENT`: the declared tolerance applies as a pass/fail gate.
     Divergence > tolerance → HALT (as in 6E.20.2 Stage 5). Divergence ≤ tolerance
     → PROCEED to §8 evaluation.
   - If `CROSS_ENVIRONMENT`: the tolerance is NOT applied as pass/fail. The divergence
     is recorded. Execution PROCEEDS to §8 evaluation. The cross-environment
     classification is reported alongside §8 results.
   - If `ENVIRONMENT_UNVERIFIABLE`: the tolerance is NOT applied as pass/fail. The
     divergence is recorded. Execution PROCEEDS to §8 evaluation. The
     environment-unverifiable classification is reported alongside §8 results.

**Effect on 6E.20.2 (informational):** Under this revised specification, the 6E.20.2
Stage 5 halt would NOT have occurred, because the historical NEPR is absent
(`ENVIRONMENT_UNVERIFIABLE`). The divergence would have been recorded and execution
would have proceeded to §8 evaluation. The halt was a consequence of the absence of
the NEPR-based classification in the original specification.

### 2.7 Amendment to §8 — Acceptance Criteria and NEPR Dependency **[NEW]** (audit condition 5)

Protocol v3.1 §8 defines acceptance criteria P1–P6 and the JOINT SUCCESS GATE. The
B0 reproducibility anchor gate (§2.6) is a PRE-REQUISITE for §8 evaluation: if the
anchor gate HALTs execution (SAME_ENVIRONMENT + divergence > tolerance), §8 is never
reached.

The following MUST be added to §8:

**NEPR classification reporting.** For any execution that includes a B0 reproducibility
anchor gate, the §8 verdict MUST include the NEPR comparison classification as metadata.
The classification does NOT affect the P1–P6 thresholds or the JOINT SUCCESS GATE
logic. It is reported alongside the verdict for interpretive context:

- `SAME_ENVIRONMENT`: §8 results are directly comparable to the reference execution.
- `CROSS_ENVIRONMENT`: §8 results are from a different environment; comparison with
  the reference execution's §8 results requires caution. The cross-environment
  classification is annotated in the outcome matrix.
- `ENVIRONMENT_UNVERIFIABLE`: §8 results cannot be compared to the reference execution
  because the reference environment is unknown. The unverifiable classification is
  annotated in the outcome matrix.

**§8 thresholds are environment-independent.** The P1–P6 thresholds (§8) are absolute
constants (§8: "none is a function of any Phase 6E.18/6E.19 observed value"). They
apply regardless of the NEPR classification. The NEPR classification affects ONLY the
B0 reproducibility anchor gate (§2.6), not the §8 acceptance criteria.

**Proposed §8 amendment text:**

> For any execution that includes a B0 reproducibility anchor gate, the verdict output
> MUST include the NEPR comparison classification (`SAME_ENVIRONMENT`,
> `CROSS_ENVIRONMENT`, or `ENVIRONMENT_UNVERIFIABLE`) as a non-gating metadata field.
> This classification does not modify the P1–P6 thresholds or the JOINT SUCCESS GATE
> logic. It is reported for interpretive context: SAME_ENVIRONMENT results are directly
> comparable to the reference; CROSS_ENVIRONMENT results require caution; and
> ENVIRONMENT_UNVERIFIABLE results cannot be compared to the reference.

## 4. Naming and Framing

This phase is titled **Reproducibility Specification and Environment Provenance
Remediation**. It is NOT framed as "a fix for the Stage 5 failure." What has been
proven:

- Stage 2 had a real semantic/API defect → proven → fixed.
- Stage 5 has a real numerical divergence → proven.
- Historical provenance is inadequate → proven.
- Runtime drift caused the divergence → **not proven** (Classification B).
- Relaxing the tolerance → **not currently justified**.

This proposal addresses the provenance and specification deficiencies that are
independently established, regardless of the unresolved root cause.

## 5. Implementation Notes

### 5.1 NEPR Collection Script

A read-only NEPR collection utility should be developed that:
- Queries all fields in categories A–F at execution time
- Serializes to canonical JSON (keys sorted, no trailing commas)
- Computes `nepr_hash` as SHA-256 of the canonical JSON excluding the `nepr_hash` field
- Writes the NEPR atomically (write to temp file, then rename)
- Is invoked automatically by any anchor-producing runner BEFORE evaluation gates
- Can also be invoked standalone for environment auditing

### 5.2 Backward Compatibility

The NEPR requirement applies to **future** executions. Historical executions (including
6E.20.1) that lack NEPRs are classified as `ENVIRONMENT_UNVERIFIABLE` — their anchors
remain recorded but cannot serve as strict reproducibility gates. Under the revised
specification, `ENVIRONMENT_UNVERIFIABLE` does NOT halt execution; it records the
divergence and proceeds to §8 evaluation.

### 5.3 Relationship to Frozen Protocol v3.1

Protocol v3.1 (`E16CA4F1…`) is frozen and MUST NOT be modified. The amendments
proposed here would take effect in a future protocol revision (v3.2 or v4.0 amendment)
that supersedes v3.1 for future executions while preserving v3.1 as the historical
record.
