# THEO v0.5 — Neural Symbolic Interface Implementation Plan

## Status

Draft — subordinate to ADR-0028. This document is deliberately experimental and
mutable; ADR-0028 is normative.

## Relationship to ADR-0028

- **ADR-0028 defines *what the architecture permits*.**
- **This document defines *how we are experimenting within it*.**

Nothing in this plan may alter the contracts frozen by ADR-0028 (protocols,

If this plan conflicts with ADR-0028, ADR-0028 wins. ADR-0028 remains

## Baseline Invariance (Hard Requirement)

> **Phase 0 must be purely additive. It must not alter the behavior of the
> canonical symbolic pipeline when no provider is configured.**

The equivalence chain that every additive step must preserve:

```
v0.4.1 symbolic runtime
→ same runtime + empty neural interface
→ identical state transition, decision, trace, replay, and benchmark results
```

This is demonstrated mechanically, not asserted:

- every pre-v0.5 test passes **unchanged**;
- new interface tests pass on top;
- `theo benchmark run` produces 35/35 PASS with decisions, traces, and state
  hashes identical to the frozen baseline for a no-provider runtime;
- replay invariant fingerprints are identical (fingerprint equality +
  cross-process determinism).

Only after no-provider equivalence is demonstrated may an actual provider
influence cognition, and then only through the five ADR-0028 hooks.

## Hard Constraints

Numbered here so the phases can refer to them. Items 1–3 are stated in full in
the sections above; item 4 is new and governs every neural phase.

1. **Baseline invariance** — the no-provider runtime is byte-equivalent to
   v0.4.1 for every observable output (Baseline Invariance above).
2. **Architectural firewall** — `theo_core` must never import `theo_providers`;
   `theo_providers` may import `theo_core.models.ports` but must never import
   `theo_core.symbolic` (Verification Harness).
3. **Determinism, replay, grounding** — providers are deterministic (or
   cross-process stable where supported), replay invariants hold, and every
   provider output is grounded against the snapshot boundary before it may
   influence cognition.
4. **Model independence** — THEO's architecture SHALL NOT depend on any
   particular neural model, model family, tokenizer, framework, or training
   methodology. The existing SLM is one implementation used to validate the
   interface; the future THEO SLM is another implementation of the same
   interface. ADR-0028 therefore defines *"THEO supports neural providers"*,
   never *"THEO uses \<model\>"*.

## Research Targets

The audit (`docs/research/weakest-domain-audit-v0.4.1.md`) posed four research
questions that the v0.5 experiments are designed to answer:

1. Can calibrated confidence improve ambiguity handling — i.e., does exposing
   remaining uncertainty to the decision policy change decision quality, not
   merely confidence values?
2. Can richer taxonomy rules (inheritance traversal, property propagation)
   increase inference engagement in the taxonomy domain?
3. Should decision policies consume confidence differently — and what is the
   empirical effect of each consumption policy on the corpus?
4. What benchmark characteristics best distinguish symbolic from neuro-symbolic
   performance (e.g., confidence-graded ambiguity vs. ranked hypothesis
   quality)?

Each phase records measurements against these questions. Negative results are
results.

## Phase 1 — Null Provider

`NullProvider` returns empty outputs for every protocol method; used as the
default in tests so the provider-call path is exercised without influence.
Phase 1 wires the **hook orchestration layer** (theo-core-owned
`ProviderCoordinator` + `ProviderResolver`) into the canonical pipeline and
proves the "zero providers == v0.4.1" equivalence through the real hook
adapter path. **Phase 1 consumes no provider output**: all five hooks are
consulted and their invocations recorded for provenance, but proposal,
calibration, and ranking outputs are not applied to cognition — that is the
deliberate work of Phases 3–5.

### Phase 1 acceptance contract

With no provider configured, the runtime MUST produce the same — byte-identical
where a canonical form exists — as v0.4.1 for every observable output:

- `DecisionRecord` (type, action_text, confidence, intent, referenced_goal,
  referenced_thoughts, accepted_hypothesis_id);
- `CycleState` transition (pre/post `checksum_cycle_state`);
- `GoldenTrace` and `golden_fingerprint`;
- cognitive fingerprint;
- replay result (state-hash invariants + fingerprint equality);
- benchmark results (35/35 PASS);
- stage ordering (`SchedulerTrace.stages_executed`);
- provenance (trace metadata);
- conflict resolution (`resolved_conflict_ids`);
- goal selection.

```
Provider configuration = None      |      v0.4.1 runtime
            │                      |            │
            ▼                      |            ▼
      v0.5 runtime                 |      S(t) ──→ S(t+1)
            │                      |            │
            ▼                      |            ▼
        S(t) ──→ S(t+1)            |       fingerprint X
            │                      |
            ▼                      |
       fingerprint X               |
```

### Phase 1 required tests

1. **Null-provider equivalence** — run the entire corpus with `providers =
   None` and with `providers = (NullProvider(),)`; cognitive outputs
   (fingerprint, decision, state hash) are identical.
2. **Cross-process equivalence** — the same comparison in two separate OS
   processes with `NullProvider` configured; digests match.
3. **Provider-resolution determinism** — capability → eligible → priority /
   name / configuration order → exactly one provider; ties are tested; no
   set/hash-order dependence.
4. **Unsupported capability behavior** — a provider that does not advertise a
   capability is never called for it, and the symbolic fallback executes.
5. **Provider failure behavior** — a provider exception becomes an explicit
   `ProviderFailure` (recorded in provenance) and fails the cycle; it is never
   silently treated as absent.
6. **Trace provenance** — traces distinguish "provider not configured" (no
   provenance key, identical to v0.4.1) from "provider configured but returned
   no proposal" (executed invocation with empty output summary).

### Phase 1 test placement

- theo-core `tests/providers/` — resolver, coordinator, failure, and pipeline
  hook tests with **stub providers** (no theo-providers dependency).
- theo-providers `tests/` — `NullProvider` corpus-equivalence and
  cross-process tests (theo-core never depends on theo-providers, even in
  tests).

### Phase 1 exit gate

- no-provider and null-provider runs are byte-identical across the corpus and
  across processes;
- 294 pre-v0.5 tests pass unchanged; new interface tests pass on top;
- `theo benchmark run` 35/35 PASS;
- replay invariants hold; mypy --strict, ruff, coverage ≥80% green;
- ADR-0028 amendment (resolution / failure / provenance) ratified with the

## Phase 3 — Heuristic Salience (Lowest Risk)

- `SalienceProvider` reorders rules and goals via lexical similarity over
  snapshot text (TF-IDF/BM25/RapidFuzz — no torch).
- Reorder only: cannot create or delete candidates.
- **Implemented:** `HeuristicSalienceProvider` in `theo-providers/heuristic/salience.py`.
- **Contract enforced:** exact same N rules/goals returned, permuted order only;
  provider declares `SALIENCE` capability; provenance recorded.
- **Measurement:** ordering must not change decisions on the corpus; telemetry
  records the reorder.
- **Result:** **Null result.** The heuristic provider produces identical
  decisions to the v0.4.1 baseline across all 51 cases (100% pass rate,
  0.47 avg fired rules, 0.96 avg confidence, 0.47 avg DAG depth). Rule
  ordering does not affect final decisions on the current corpus.
- **Interpretation:** The v0.4.1 limitation is deeper than rule selection —
  the symbolic inference engine is order-independent for the current knowledge
  base, or the corpus lacks cases where competing rules have overlapping
  conclusions. This null result is scientifically valid and directs effort to
  Phase 4 (calibration).
- **Exit gate:** decisions/traces identical where order is neutral; no benchmark
  regression; all gates green.

## Phase 4 — Heuristic Calibration

- `CalibrationProvider.score_hypotheses` + `score_confidence` using lexical
  evidence support (formula chosen here experimentally).
- **Risk:** changes confidence values, so the decision policy's consumption must
  be re-verified under Mode A.
- **Measurement:** confidence distribution becomes discriminating without
  changing decisions; benchmark passes under Mode A.
- **Exit gate:** 35/35 PASS; confidence distributions recorded; any decision
  changes are deliberate, measured, and approved.

### Phase 4 result — outcome A (strong), 2026-08-09

Competition-aware recalibration implemented in `HeuristicCalibrationProvider`
(theo-providers). Root cause of the v0.4.1 compression: in hypothesis-collection
order the percept-self hypothesis (`hypothesis://cand/N`, confidence 1.0) nearly
always precedes belief readings (0.5–0.95), so rule-less decisions carry a flat
1.0. The provider discounts that 1.0 by reading count and top-margin
(`discount = 0.10*competition + 0.05*top_gap − 0.10*min(margin, 0.5)`, clamped
≥0, calibrated value clamped to `[0.90, decision.confidence]`); rule-derived
(`conf < 1.0`) and single-hypothesis decisions pass through unchanged. Output is
bounded `0 ≤ score ≤ 1`, deterministic (same input + version + seed →
identical, replay-verified via fresh coordinator).

Results on the 51-case corpus (Baseline = v0.4.1 frozen; Null = provider
configured but inert):

| Metric | Baseline | Null | Calibration |
|---|---|---|---|
| Pass rate | 100.00% | 100.00% | 100.00% |
| At confidence 1.0 | 86.27% | 86.27% | 25.49% |
| Mean confidence | 0.9637 | 0.9637 | 0.9447 |
| Confidence variance | 0.010008 | 0.010008 | 0.009147 |

- Decision changes vs baseline: **0**; `DecisionRecord` identity preserved
  (winner + decision ID untouched).
- Replay deterministic across fresh coordinators: **True**.
- Informative discrimination: Spearman(confidence, hypothesis_count) over the
  baseline==1.0 window = **−0.856**; mean confidence single-hypothesis =
  1.0000 (n=7) vs multi-hypothesis = 0.9738 (n=37). Confidence now correlates
  with ambiguity; not merely spread (outcome A/strong).
- The `Hurricane` uncertainty case stays at 0.60 (rule-derived) — untouched by
  design.

Next (Phase 5) consumes only well-formed `ScoredHypothesis` outputs from
`score_confidence`; any other output shape remains ignored (Phase 1 pin).

### Scientific qualification (strong heuristic result, not yet statistical calibration)

The −0.856 Spearman correlation demonstrates that heuristic confidence is
strongly related to hypothesis multiplicity/ambiguity. It does **not** yet
establish statistical calibration against empirical correctness probabilities.
The immediate v0.5 hypothesis is proven: the confidence-compression problem can
be substantially reduced without modifying symbolic decisions. A later
measurement layer should add reliability diagrams, Brier score, expected
calibration error (ECE), confidence-vs-correctness, and calibration across
domains rather than hypothesis count alone.

## Phase 5 — Heuristic Proposals (Highest Risk)

- `HypothesisProposalProvider` proposes hypotheses via lexical retrieval over
  the knowledge base; grounding enforced strictly (no `grounded=False`
  fallback).
- `RuleDiscoveryProvider` runs **offline**: driven by benchmark failures and
  `KnowledgeGapReport`; proposed rules are never auto-committed.
- **Measurement:** proposal acceptance rate, grounding rejection rate, decision
  impact, benchmark pass-rate delta.
- **Exit gate:** grounding-passing proposals do not reduce benchmark pass rate;
  failures analyzed via `GapAnalyzer`.

### Phase 5 result — outcome B (null, informative), 2026-08-10

`HeuristicHypothesisProposalProvider` (proposal-only, never auto-accepted) ran
**blind** against the frozen 51-case corpus.

| Metric | Value |
|---|---|
| Baseline / proposal-config pass rate | 51/51 both |
| Decision changes | 0 |
| Replay deterministic | True |
| Counterfactual reconstruction (symbolic-only reproduces actual decision) | OK, all 51 |
| Cases with ≥1 proposal / total proposals | 23/51, 25 |
| Grounded / rejected / novel proposals | 25 / 0 / 25 |
| Rule-conclusion proposals (of fired rules / unfired) | 17 / 2 |
| Counterfactual decision flips — naive source scoring | 6 (all uncertainty domain) |
| Counterfactual decision flips — epistemic (propagated-confidence) scoring | 0 |
| Conflicts exposed: baseline vs merged | 64 → 89 |

**Primary finding — candidate generation is THEO's missing capability, not
reasoning.** The symbolic `HypothesisEngine.generate_hypotheses` gates candidates
on exact percept-token overlap with belief propositions. Rule-derived conclusions
(e.g. UNC-001: rule `rain → "The ground is wet"`, which *fired* during inference)
never become decision candidates because their text shares no tokens with the
percept. The heuristic provider — operating only lexically on the same snapshots —
surfaces exactly those derived conclusions: 17 rule-conclusion proposals, 15
referencing rules that fired, all novel, all grounded. This is the Phase 5
positive signal: heuristic candidates expose information the symbolic generator
cannot produce.

**Measurement-honesty finding — the naive flips are scoring artifacts.** The 6
counterfactual flips occur only when proposals are scored at the referenced
rule's intrinsic salience (1.0). Scored at the propagated confidence of the
already-derived conclusion belief (0.5 = percept × 0.5 multiplier), the merged
candidate set changes **0/51** decisions: the incumbent percept-self
interpretation is genuinely higher-confidence. So (a) no benchmark regression
would follow from accepting proposals at propagated confidence, and (b) the
proposal-only design is confirmed necessary — naive auto-acceptance would have
double-counted rule salience and produced regressions.

**Secondary observations:** mean raw confidence of the winning decision drops
−0.0674 when proposals compete (competition compresses the winner's margin);
merging exposes +25 additional conflict records (64 → 89); calibration on the
merged set yields mean 0.8885. Blind run confirmed the provider threshold
constants (`_TOP_N=5`, `_MIN_SIMILARITY=0.25`) were not tuned against the corpus.

**Scientific qualification:** this is a *candidate-coverage* result, not a
decision-quality result. It shows the symbolic generator's coverage gap and that
a lexical adapter closes it without regressing decisions. Whether the exposed
candidates are *better* decisions remains untested (proposal-only by design);
that question belongs to a future acceptance-enabled Phase 5 follow-up with its
own baseline governance.

## Phase 6 — Reference SLM & Neural Boundary Validation

The purpose of Phase 6 is **not** to build the final THEO model. It answers one
question:

> Can a real semantic language model provide measurable value through the
> neural-symbolic boundary without changing symbolic cognition?

An existing small SLM is used as a **reference / control implementation**, not
as THEO's permanent intelligence.

### The reference SLM is NOT THEO

This is an experiment-governance rule and lives in the implementation plan, not
in ADR-0028:

- The reference SLM is an experimental provider used to validate the neural
  interface. It SHALL NOT become a dependency of theo-core, SHALL NOT define
  the architecture, and SHALL NOT be required for symbolic operation.

```
theo-core          works without any model
theo-providers     reference SLM remains optional
```

- Consistent with Constraint 4, the SLM cannot create Beliefs, Thoughts,
  Decisions, Rules, or Conflicts; the provider protocols and snapshot boundary
  enforce this mechanically.

#### 6A gate — Interface Validation

Before asking whether the SLM improves reasoning, prove the architecture
actually works. The reference SLM must pass:

- snapshot isolation
- provider protocol compliance
- capability discovery
- grounding verification
- provider provenance
- model hash recording
- replay
- cross-process determinism where supported
- 51-case benchmark
- mypy
- ruff

This answers: *Can an actual model fit cleanly into the architecture we
designed?* Only then do we evaluate intelligence.

#### 6A success criteria — two independent questions

The old criterion ("SLM passes 51/51") is too weak. It is replaced by two
independent questions.

**Architecture success** (binary, all-or-nothing):

| Contract | Status |
|---|---|
| Provider contract | PASS |
| Grounding | PASS |
| Replay | PASS |
| Provenance | PASS |
| Isolation | PASS |
| Cross-process | PASS |

**Cognitive success** (measured, scalar):

- decision delta
- correct decision changes
- incorrect decision changes
- grounded proposal rate
- novel proposal rate
- useful proposal rate
- unsupported proposal rate
- hypothesis count
- conflict count
- fired rules
- DAG depth
- derived beliefs
- confidence distribution
- calibration metrics
- per-domain performance

An SLM can therefore be **architecturally successful but cognitively useless**.
That is a perfectly valid result.

### 6B — THEO SLM Design

Do not start training immediately after 6A. First design the model.

**Deliverable: `docs/research/theo-slm-design-v0.md`** (not ADR-0028 — see the
governance rule below).

Determine the **model objective** first. Initial target:

> semantic interpretation + candidate generation + evidence relevance

rather than a general-purpose conversational model.

Define:

- parameter budget
- context length
- tokenizer
- vocabulary
- architecture
- number of layers
- hidden dimension
- attention heads
- positional encoding
- training objective
- pretraining corpus
- instruction corpus
- reasoning corpus
- evaluation corpus
- quantization strategy
- inference target
- latency target
- hardware constraints

And most importantly, **what the model DOES NOT learn**. THEO's symbolic runtime
already handles:

- belief state
- provenance
- contradiction resolution
- rule execution
- state transitions
- goal commitment
- decision authority
- replay
- verification

Your SLM therefore does not need to duplicate any of that — a large advantage
over a general-purpose model.

project rather than an implementation exercise.

### Phase 6 governance — ADR-0028 does not freeze the model

ADR-0028 freezes the **interface**: provider protocols, the snapshot boundary,
grounding, replay, determinism, dependency direction, provider purity, and
capability discovery.

ADR-0028 does **not** freeze the **implementation**: Transformer architecture,
parameter count, tokenizer, dataset, training algorithm, model family, attention
mechanism, quantization, PyTorch, Hugging Face, Phi/Qwen/etc.

Those belong in `docs/research/theo-slm-design-v0.md`, or in a model-specific
ADR if the architecture eventually becomes important enough. ADR-0028 must
remain *"THEO supports neural providers."*

## Phase 7 — Explanation Research (Research-Only)

Comes after the first SLM research cycle (Phase 6), not as the immediate next
implementation.

- `ExplanationProvider` is **research-only** — it is NOT a runtime protocol and
  lives under `evaluation/research/`.
- Uses captured traces plus provider outputs to generate post-hoc explanations.
- **Exit gate:** research report; no runtime contract change.

## Rollback Criteria

- Any phase that violates ADR-0028, changes a pre-v0.5 test's expectations,
  alters no-provider behavior, or fails the benchmark/replay gates is rolled
  back to the last green commit.
- A provider that cannot guarantee benchmark determinism is excluded from the
  benchmark gate — it is not removed from the repository.
- If a provider underperforms the v0.4.1 baseline on the corpus, it is removed
  and the phase is closed as a documented negative result.

## Commit Discipline

- One commit per phase or per meaningful deliverable; governance commits
  separate from code commits.
- ADR-0028 stays **Proposed** until its ratification commit; no plan text may
  claim the architecture is frozen before then.
